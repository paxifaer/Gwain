## Judgment calls (documented)

- **Flat dotted selector keys** (`status.url`, `start.url`, …) —
  JUSTIFIED. `SelectorMap = BTreeMap<String, String>` at
  `src/spec/schema.rs:15`; a nested yaml mapping cannot deserialize
  into a flat string-valued BTreeMap. D-111's selector sketch is
  itself flat (`{"url": "...", "method": "POST"}` per-key) so the
  chosen `status.url` dotted encoding is the minimal faithful
  encoding of D-111 given the SelectorMap constraint. Justification
  documented at `src/providers/http.rs:12-25` (table format) and in
  `examples/registry-robot.yaml:290-291` — "selector 必须是 FLAT
  dotted keys(SelectorMap=BTreeMap<String, String>；数值要加引号)".
  Confirmed NOT a deviation from the spec.

- **Explicit-version reqwest (instead of `workspace = true`)** —
  JUSTIFIED as a conservative choice. Workspace pins
  `reqwest = { version = "0.12", features = ["json"] }` at the
  workspace `Cargo.toml:30` (without `default-features = false`).
  The crate entry is `reqwest = { version = "0.12",
  features = ["json", "rustls-tls"], default-features = false }`.
  `cargo tree -p demo-app-lifecycle -i reqwest` shows ONLY rustls
  features (`__rustls`, `rustls-tls-webpki-roots-no-provider`,
  rustls v0.23.40 in the graph) — `native-tls`, `default-tls`,
  `libreSSL`, `openssl-sys` are absent. The crate-level comment at
  Cargo.toml:32-38 documents the cargo 1.95 workspace-inheritance
  quirk (member's `default-features = false` does NOT reliably
  cancel workspace-carried default features). Whether the strict
  workspace form would have sufficed on cargo 1.95 is debatable;
  the explicit form unambiguously produces the desired feature set.
  Net effect is correct.

## Concerns (non-blocking)

1. **Response body not drained in `send()`**: http.rs reads
   `resp.status()` and drops the Response without consuming the body.
   Reqwest's connection pool cannot reuse the connection when the
   body is unread; every HTTP round-trip therefore closes its TCP
   socket. For the dogfood poll rates (one status probe every
   OBS_TICK ≈ 200ms per service, plus occasional control ops), the
   kernel-level socket setup cost is negligible; for a future
   high-frequency probe consumer, a `resp.bytes().await` (or
   `.text().await`) drain would pay off. Documenting as a follow-up
   rather than a P4 blocker because the contract (status/control
   correctness) is unaffected.
2. **No default `Content-Type: application/json` on POST bodies**:
   When `body` is supplied in a verb sub-object, the request body is
   sent verbatim without an automatic `Content-Type` header. roboctl
   may or may not enforce Content-Type matching; if it does,
   operators must add `'{"Content-Type": "application/json"}'` via
   the `headers` sub-object field manually. Verbatim-body is the
   documented behavior (http.rs §"<verb>.field" table); acceptable
   for P4 but worth noting before dogfood.
3. **`user_agent` config not asserted in any test**: provider config
   accepts a `user_agent` override (http.rs:214-217); no P4 test
   reads the stub's User-Agent line. The default
   `argowatch-lifecycle/1.0` is set unconditionally and the override
   path is a single string-passthrough; risk is minimal. Additive
   follow-up if dogfood cares.
4. **`default_timeout_ms` is provider-wide**: per-sub-object
   override via `<verb>.timeout_ms` selector key works
   (http.rs:299-310), but a provider-wide default that differs per
   verb requires a second instance. Consequence of the XOR-token
   trade-off + provider-wide default; documented in http.rs §Selector
   flat-key encoding table. Acceptable.
