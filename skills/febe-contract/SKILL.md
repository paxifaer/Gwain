# febe-contract：前后端联调契约工作流

目标：一个跨端功能落地后，「点什么、发什么、后端答什么、界面变成什么、怎么证明」全部有据可查，且最终验收标准由用户批准。

## 何时使用

- 前端按钮、表单、状态与后端接口对接。
- 跨端功能：UI ↔ REST/RPC ↔ 服务 ↔ 设备或数据源。
- 接口对不上：按钮报 405、字段 `undefined`、双端 schema 漂移、半部署版本错配。
- 用户要求「联调」「验收标准」「前后端一起改」「做稳定点」。

## 阶段 0：需求澄清门（不通过不得开工）

1. 逐字记录用户原始需求到 `requirement.md`，不做语义改写。
2. 找出需求中的语义歧义：动作对象、范围、目标机器、数据来源、恢复行为、边界条件。
3. 每个歧义给 2-3 个选项问用户，禁止自行选择。示例见 `examples/close-audio-chain.md`。
4. 用户确认后冻结需求；需求变更必须重新确认。
5. 问不到的假设写进 assumption 栏并明示「待确认」，不得沉默补齐。

## 阶段 1：契约四表

依次填写，模板在 `templates/`：

1. `contract-table.md` — 接口契约：path、method、请求/响应 schema、错误语义、幂等、副作用。
2. `ui-api-map.md` — 按钮↔接口映射：UI 事件 → 请求 → 预期响应 → 预期 UI 反应 → 异常时 UI 反应。
3. `test-boundaries.md` — 测试边界：每层测什么、mock 到哪、什么必须真连、证据形态。
4. `acceptance.md` — 验收标准：单条单判，含场景、前置、操作、期望、证据层、反例。

schema 同源优先：后端导出 OpenAPI（如 `utoipa`）→ 前端生成类型（如 `openapi-typescript`）→ 运行时校验（如 `zod`）。禁止双端手写同一份 schema。配置方法见 `references/api-alignment.md`。

## 阶段 2：用户批准门

- 验收标准表连同证据要求逐条给用户，获得显式同意后才开始改代码。
- 修改任何一条验收标准 = 旧证据作废，重新批准。
- agent 永远不自判「通过」；完成态只写 `READY_FOR_USER_ACCEPTANCE`。
- 验收标准必须和需求逐条对应：需求里没有的不加码，需求里有的不遗漏。

## 阶段 3：实现与联调

- 顺序：先契约（schema/类型生成）→ 后端实现 → 前端绑定 → 分层测试。
- mock 边界按 `templates/test-boundaries.md` 分层执行（L2 起被测前后端必须真实，设备/外部依赖可 mock），证据级别不得低于验收条目要求。
- 试验环境必须独占端口与 topic namespace、使用虚构 robot/fleet ID；依赖共享（软链他人仓库、公共端口）时必须在交付里显式声明，启动前核对实际 endpoint/topic 不与他人冲突。
- 切换数据源（mock → 真实）后必须核验来源标识、数据新鲜时间与真实观测，未完成不得进入验收。
- 每层完成即存证据：原始命令输出、退出码、真实请求/响应、版本号或构建标识。
- 部署类变更核对全部组件版本一致后再宣布上线；单组件成功不算成功。

## 阶段 4：对抗验收

1. 独立验证者只拿三样：冻结需求、验收标准、实现声明。不给实现者的自辩材料。
2. 授权语固定为「证伪，不是确认」。重点反例：
   - 测试通过但用户目标未达成。
   - 按钮绑定死接口或旧版本协议。
   - mock 数据冒充真后端。
   - 层级替代：浏览器检查顶替真实链路，静态检查顶替动态测试。
   - 0 执行、用例数量短缺、必测被忽略仍报绿。
   - 「没有报错」被当成正向证据。
3. 每条结论必须附原始命令输出、文件行号、退出码；缺证据即「未证明」。
4. 对抗深度有上限：每条验收标准一轮证伪；连续两轮无新增问题即收敛，不追求清零。

## 红旗（出现即停）

- 开工前没有用户批准的验收标准。
- 实现者自己写「验收通过」或自行解释需求语义。
- 用「没有报错」「进程活着」代替正向证据。
- 双端 schema 手写两份，或验收时才核对接口。
- 改了验收标准却没重新找用户批准。
- 工具调用被策略拒绝时原样重试同一调用：改方案或如实报告阻塞。
