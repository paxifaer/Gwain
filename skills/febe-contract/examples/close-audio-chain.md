# 示例：「关闭音响」链路契约包

真实案例。用户一句话需求，agent 当时两处跑偏；按本 skill 的正确走法如下。

## 阶段 0：需求澄清

用户原话（逐字冻结）：

> 我说的关闭音响是，关闭正在播放的音响服务不是静音

识别出的歧义与应问的选择题（当时没问，直接实现就跑偏了）：

1. **停止对象**：A. 只停当前这一段声音；B. 停这个告警的全部播报；C. 关闭整个音响服务。
2. **恢复行为**：告警未解除、再次触发时响不响？解除后响不响？
3. **目标范围**：全局所有告警，还是只当前告警？试听受不受影响？

**已冻结（用户 2026-10-22 确认）**：语义 = 静默本次触发——正在响的停掉、本次触发不再重播、告警照常显示；解除后再触发恢复响；「恢复播报」按钮立即恢复全部静默。历史注记：当时 agent 未经确认自行实现了这套语义，事后才补确认——这正是阶段 0 要防的错误：**先问再做，不把实现结果倒推成「用户预期」**。

另一起歧义：「部署在对面机器上」的「对面机器」= 本机还是 192.168.100.100？应直接给机器选项让用户选。

## 契约（节选）

| ID | path | method | 响应 | 错误语义 | 幂等 | 副作用 |
|---|---|---|---|---|---|---|
| C-01 | `/api/argodog/audio/stop` | POST | `AudioStopResponse{ok, stopped, error, request_id, operation, source}` | 409 忙 / 504 超时 | 是 | 静默当前播报与本次触发；不改告警状态 |

计数定义（历史坑：`stopped:2` 含义不清）：`stopped` = 被静默的播报条数，按 occurrence 计，当前正在播的段与同一 occurrence 只计一次；空闲时为 0。

## 映射（节选）

| ID | 控件 | 预期 UI 反应 | 异常反应 | 覆盖测试 |
|---|---|---|---|---|
| U-01 | 音响卡片「关闭音响」 | 显示「已停止 N 条播报」 | toast 报错并显示失败原因 | jsdom 页面测试（L2，mock API 层）；L3 浏览器实测未覆盖〔缺口〕 |

## 测试边界

| 验收点 | 最低层 | 备注 |
|---|---|---|
| 响应字段与 schema 一致 | L1 | 漂移门禁 |
| 按钮点击显示结果行 | L3〔缺口：现有证据为 jsdom L2〕 | 浏览器实测未做，如实标注，不用组件测试冒充 |
| 声音真的停止 | L4 | 人耳/录音；API 成功不算 |

## 验收条目（节选）

| A-ID | 操作 | 期望 | 证据层 | 反例 |
|---|---|---|---|---|
| A-01 | 播放中点击「关闭音响」 | 结果行显示「已停止 1 条播报」 | L3 | 静音徽标出现（旧语义）判 FAIL |
| A-02 | 空闲时点击 | 显示「当前无播报」，`stopped:0` | L2 | 报错或计数非 0 判 FAIL |
| A-03 | 停止后告警仍 ACTIVE | 告警卡保持显示 | L2 | 告警消失判 FAIL |

## 对抗记录（节选）

用户实测报「音响开关操作失败，method not allow」。正确取证顺序：

1. 抓用户侧实际请求：方法 + 路径 + 响应码。
2. 对照契约表：旧路径 `/api/argodog/audio` 返回 405，新路径 `/api/argodog/audio/stop` 返回 200 → 最可能解释是「浏览器运行的旧 bundle 绑定了旧接口」（**推断，未最终证实**：未抓到用户侧 bundle 版本，强刷后无回报确认）。
3. 修复后按 L3 重新实测，不允许用 curl 成功代替用户浏览器成功。

当时的错误做法：直接断言「浏览器缓存」是根因——只验证了新旧路径差异就跳到结论。正确做法是把定性写成「推断，未证实」，直到拿到 bundle 版本或用户确认。
